# CLAUDE.md

This file defines the mandatory conventions for `payment-manager-frontend`, the React client of the `payment-manager` API. All generated or modified code under `frontend/` MUST comply with these rules. The backend conventions in `.claude/CLAUDE.md` do NOT apply here, except where this file explicitly mirrors them.

## Project Context

- Project name: `payment-manager-frontend` (folder `frontend/` inside the `payment-manager` repository)
- Language: TypeScript in `strict` mode
- UI library: React (single-page application, client-side rendering only, no SSR)
- Build tool: Vite, with npm as the package manager (Node 24)
- UI components and styling: Mantine (`@mantine/core`, `@mantine/hooks`, `@mantine/notifications`, `@mantine/modals`) with `postcss-preset-mantine`
- Server state: TanStack Query
- Routing: React Router (library mode)
- Forms and validation: react-hook-form + zod
- Testing: Vitest + Testing Library + MSW; Playwright for end-to-end tests
- API contract: TypeScript types generated from the backend OpenAPI document (springdoc, `/v3/api-docs`)

Exact versions are defined in `package.json`, which is the single source of truth.

### Common Commands

```bash
npm install          # install dependencies
npm run dev          # start the dev server on http://localhost:5173 (proxies /api to http://localhost:8080)
npm run test         # run unit and component tests (Vitest)
npm run lint         # run ESLint
npm run build        # type-check and build for production
npm run gen:api      # regenerate src/api/schema.d.ts from the running backend's /v3/api-docs
npm run test:e2e     # run Playwright end-to-end tests against the full stack
```

Every change MUST pass `npm run lint`, `npm run test`, and `npm run build` before it is merged.

## 1. Folder Structure

Code is organized **by feature**, not by technical type:

```
src/
├── api/                  # HTTP layer: generated schema, fetch client, endpoint functions
├── features/
│   └── payments/
│       ├── hooks/        # TanStack Query hooks (queries and mutations)
│       ├── components/   # presentational components of the feature
│       ├── pages/        # route-level components that orchestrate hooks and components
│       ├── schemas.ts    # zod schemas of the feature's forms
│       └── queryKeys.ts  # query key factory of the feature
├── shared/
│   ├── components/       # cross-feature components (ErrorState, EmptyState, PageLoader)
│   └── lib/              # cross-feature utilities (formatting)
└── app/                  # router, providers (MantineProvider, QueryClientProvider), theme, and the root App component
tests/
├── setup.ts              # Testing Library, MSW, and jsdom polyfills required by Mantine (matchMedia, ResizeObserver)
├── render.tsx            # custom render that wraps components in MantineProvider and QueryClientProvider
├── mocks/                # MSW handlers and test data builders
└── e2e/                  # Playwright specs
```

`shared` holds only code used by more than one feature. Feature-specific code MUST NOT be placed in `shared`.

## 2. Layering and Dependencies

The dependency direction MUST be **pages → hooks → api**.

| Layer | Responsibility | Allowed Dependencies |
|-------|----------------|----------------------|
| **api** | Perform HTTP requests and translate error responses into `ApiError`. No React code. | Generated schema |
| **hooks** | Wrap api functions in TanStack Query queries and mutations, including cache updates and invalidation. | api, queryKeys |
| **pages** | Read route and URL state, call hooks, handle loading/error/empty states, and compose components. | hooks, components, shared |
| **components** | Render data received through props and emit events through callbacks. | shared |

Rules:

- Presentational components MUST NOT call hooks from `hooks/`, TanStack Query, or `fetch`. They receive data and callbacks through props.
- Components MUST NOT call `fetch` directly; all HTTP access goes through `src/api`.
- Use named exports only. Default exports are forbidden, except where a tool requires them (e.g., config files).
- Use function components only.

## 3. API Layer

- Types of requests and responses MUST come from the generated `src/api/schema.d.ts` and be re-exported with friendly names from `src/api/types.ts` (e.g., `Payment`, `PaymentStatus`, `PageResponse<T>`). Do NOT hand-write types that duplicate the backend contract.
- `src/api/schema.d.ts` is generated by `npm run gen:api` and MUST NOT be edited manually. Regenerate it whenever the backend contract changes.
- The browser always calls relative URLs under `/api`. The prefix is stripped by the Vite dev proxy and by nginx in Docker, so no backend URL is hardcoded.
- Every non-2xx response MUST be converted into an `ApiError` by `src/api/client.ts`. `ApiError` parses the backend `ProblemDetail` (RFC 9457) and exposes `status`, `title`, `detail`, and `fieldErrors` (the `errors` map returned on `400 Bad Request`).
- Network failures MUST also surface as `ApiError` with a generic, user-friendly message.

## 4. State Management

Each kind of state has exactly one home. A global store (Redux, Zustand, or a state Context) MUST NOT be introduced.

| Kind of state | Where it lives |
|---------------|----------------|
| Server data (payment list, payment detail) | TanStack Query cache |
| Filters and pagination | URL search params (`useSearchParams`) |
| Form values and errors | react-hook-form |
| Local UI state (open modal, etc.) | `useState` or `useDisclosure` in the owning component |

Rules:

- Server data MUST NOT be copied into `useState`.
- Query keys MUST be built exclusively through the feature's `queryKeys.ts` factory; inline array keys are forbidden.
- After a mutation, update the cache with `setQueryData` when the response contains the updated entity, and invalidate the affected lists with `invalidateQueries`.
- A refund that fails with `409 Conflict` MUST show the backend `detail` and refetch the payment, so the UI reflects the real state.

## 5. Forms and Validation

- Every form MUST be validated with a zod schema connected through `zodResolver`. The form type MUST be inferred with `z.infer`; do NOT declare it separately.
- Client-side rules MUST mirror the backend `CreatePaymentRequest` constraints: `merchantId` not blank and at most 100 characters; `amount` greater than zero with at most 2 decimals; `currency` required (`ARS`); `simulationResult` is `APPROVED` or `REJECTED`.
- Backend validation errors (`ApiError.fieldErrors`) MUST be mapped to the matching fields with `setError`. Errors without a matching field are shown as a form-level message.
- Submit buttons MUST be disabled while the request is pending.

## 6. UI and UX

- Use Mantine components and layout primitives (`AppShell`, `Stack`, `Group`, `Table`, `Badge`, `Modal`, etc.). Do NOT add another component library, Tailwind, or a CSS-in-JS solution.
- Styling MUST use, in this order of preference: component props (`variant`, `color`, `size`), Mantine style props (`mt`, `p`, `c`, etc.), and CSS Modules (`<Component>.module.css`) for anything else. Inline `style` objects are forbidden.
- Colors, spacing, and fonts MUST come from the theme defined in `src/app/theme.ts`; do NOT hardcode values.
- Every data view MUST handle its loading, error, and empty states explicitly.
- User feedback for mutations MUST use notifications from `@mantine/notifications`. A `REJECTED` payment is a valid business outcome, not an error: show it as a warning, not as a failure.
- Destructive or irreversible actions (refund) MUST ask for confirmation with `modals.openConfirmModal` from `@mantine/modals`.
- The refund action MUST only be shown for payments with status `APPROVED`.
- Interactive elements MUST be accessible: use semantic elements, associate every input with a label, and keep keyboard navigation working.

## 7. Money and Dates

- Amounts MUST NOT be used in arithmetic on the client. They are only validated and displayed.
- Amounts MUST be formatted with `Intl.NumberFormat('es-AR', { style: 'currency', currency })`.
- Dates are received in UTC (ISO 8601) and MUST be displayed in the user's local time with `Intl.DateTimeFormat('es-AR')`.
- All formatting MUST go through `src/shared/lib/format.ts`; do NOT call `Intl` inline in components.

## 8. Testing (BDD)

Tests follow the same BDD principles as the backend.

- Test names MUST describe the scenario with the **given / when / then** structure: `describe` names the unit under test, and each `it` uses the format `given <precondition>, when <action>, then <expected outcome>`.
  - Example: `it('given an APPROVED payment, when the refund succeeds, then shows the REFUNDED status')`
  - Example: `it('given an amount of zero, when the form is submitted, then shows a validation error and sends no request')`
- Comments such as `// given`, `// when`, `// then` (or `// arrange`, `// act`, `// assert`) are **forbidden**. Phases MUST be separated only by a blank line.
- Each test MUST verify a single behavior.
- Query elements the way a user finds them: `getByRole`, `getByLabelText`, `getByText`. `getByTestId` is a last resort.
- Simulate user interaction with `@testing-library/user-event`, not `fireEvent`.
- Render components with the custom `render` from `tests/render.tsx`, never with Testing Library's `render` directly, so every test runs inside `MantineProvider` and a fresh `QueryClient`.
- Mock the network with MSW handlers. Do NOT mock `fetch`, api functions, or TanStack Query hooks.
- Failure scenarios MUST assert that the UI state did not change (e.g., after a `409` on refund, the status is still shown as before), not only that an error message appeared.
- Unit and component test files live next to the code they test, named `<Name>.test.ts(x)`. Shared setup, MSW handlers, and Playwright specs live in `tests/`.

## 9. General Code Style

- `any` is forbidden. Use `unknown` and narrow it.
- Code MUST be self-explanatory through clear naming; avoid redundant comments.
- Prefer immutability: `const`, `readonly` props, no mutation of props or cached data.
- File names: `PascalCase.tsx` for components, `camelCase.ts` for everything else. Hooks start with `use`.
